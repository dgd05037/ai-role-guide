# AI 역할별 작업 가이드

AI와 질문·설계·구현 이해를 함께 논의하고 구현·검증·사용자 관점 검토를 나눠 진행하기 위한 범용 지침입니다. 작업자는 전체 방향과 범위를 결정하고, 각 AI 대화에는 역할과 필요한 자료를 명시합니다.

이 저장소는 짧은 문서로 구성된 작업 지침 묶음입니다. 별도 설치, 특정 모델, MCP, 자동 실행 프로그램을 요구하지 않습니다. 대화 간 메시지 전달이나 권한 차단을 자동으로 수행하지 않으며, 사용자의 확인과 각 환경의 실제 권한 설정이 필요합니다.

## 파일과 역할

| 파일 | 읽을 대상 | 담당 범위 |
| --- | --- | --- |
| [COMMON.md](COMMON.md) | 모든 역할 | 근거, 작업 범위, 전달, 검증, 사용량 원칙 |
| [A-DESIGN.md](A-DESIGN.md) | 설계·이해 파트너 A | 다양한 질문에 답하기, 아이디어 비교, 요구사항·설계·작업 지시, 실제 구현 이해 |
| [B-BUILD.md](B-BUILD.md) | 구현 담당 B | 이번 단계 구현, 테스트, 결과 보고 |
| [C-REVIEW.md](C-REVIEW.md) | 검증 담당 C | 요구사항 대조, 독립 검증, 재현 근거와 판정 보고 |
| [D-USER.md](D-USER.md) | 사용자 관점 담당 D | 사용 흐름과 예외 검토, 추가 확인 질문 |
| [TEMPLATES.md](TEMPLATES.md) | 필요한 역할만 | 질문·결정·실행 검증·인수인계 양식 |

A는 작업 전반을 함께 생각하는 대화 파트너입니다. 개념이나 도구가 궁금할 때, 오류를 해석할 때, 방향을 비교할 때도 A와 이야기할 수 있습니다. A와의 논의에서 확정된 구현 작업은 B에 전달하고, 실제 동작의 독립 검증은 C가 맡습니다.

## 빠른 시작

1. 허용된 환경에 이 지침을 준비합니다. 공개 저장소 사용, 다운로드, 외부 도구 연결의 허용 여부는 해당 작업 환경의 규정을 확인합니다.
2. 각 대화의 실제 작업 폴더와 지침 폴더를 확인합니다. 서로 다른 위치일 수 있습니다.
3. 각 대화에 COMMON.md와 담당 역할 파일의 정확한 경로를 전달합니다.
4. 기존 프로젝트의 요구사항·실행·검증 문서를 확인하고 재사용합니다. 이 가이드의 문서 이름을 맞추기 위해 기존 파일을 덮어쓰지 않습니다.
5. 먼저 A와 요구사항 및 이번 작업을 확정합니다. 필요한 시점에 D의 관점을 검토합니다. B의 구현 후 C가 검증하는 동안 A와 실제 구현을 이해하고, 검증 결과를 받아 직접 확인합니다.

Git으로 내려받는 경우 허용된 작업 위치에서 다음 명령을 사용합니다. 같은 이름의 guide 폴더가 이미 있으면 내용을 확인하고 다른 새 폴더 이름을 선택합니다. 이 명령은 AI 대화 입력란이 아닌 셸에서 실행합니다.

```sh
git clone https://github.com/dgd05037/ai-role-guide.git guide
```

문서를 내려받았다는 사실만으로 AI에 자동 적용되는 것은 아닙니다. 아래 시작 지시처럼 읽을 파일과 역할을 명시하고 이해한 내용을 확인합니다. AGENTS.md 자동 적용이나 하위 폴더 탐색 동작에 의존하지 않습니다.

## 각 대화에 보낼 시작 지시

아래 경로는 예시입니다. 실행 환경의 실제 경로로 바꿔 전달합니다.

### A 설계·이해 파트너

```text
guide/COMMON.md와 guide/A-DESIGN.md를 읽어 줘. 너는 나와 함께 생각하는 A 설계·이해 파트너야.
실제 과제 폴더와 원본 업무 지시서의 위치부터 확인해 줘. 이 가이드의 README와 원본 업무 지시서를 구분해.
아직 구현하거나 설치하지 말고, 나와 목적·필수 조건·모호한 부분을 정리하자.
내 질문에 먼저 답하고, 개념·도구·오류·진행 방향도 함께 이야기해 줘. 제안과 확정한 결정은 구분해 줘.
필요한 질문을 중요한 순서로 제안하고, 답에 따라 무엇이 달라지는지 설명해 줘.
구현 이후에는 실제 코드와 B의 보고를 읽고, 데이터 흐름·선택 이유·한계를 내가 이해하도록 도와줘.
C의 검증이 진행 중이면 코드에서 설명한 내용과 실행으로 확인된 내용을 구분해 줘.
```

### B 구현 담당

```text
guide/COMMON.md와 guide/B-BUILD.md를 읽어 줘. 너는 B 구현 담당이야.
지정한 프로젝트의 확정 요구사항과 현재 작업 지시를 읽고 작업 번호·버전·수정 범위를 요약해 줘.
중요한 충돌이나 미확정 업무 규칙이 없다면, 승인된 이번 단계만 구현하고 실제 검증 결과를 보고해.
자료가 없거나 이번 단계가 아직 확정되지 않았다면 구현하지 말고 알려 줘.
```

### C 독립 검증 담당

```text
guide/COMMON.md와 guide/C-REVIEW.md를 읽어 줘. 너는 C 독립 검증 담당이야.
확정 요구사항과 이번 작업의 완료 기준을 먼저 읽고, 구현 코드와 보고서를 비교해 줘.
대상 작업 번호·버전과 검사할 코드 상태를 기록하고, 검증 중 관련 파일이 바뀌면 영향을 확인해 줘.
구현 코드를 직접 고치지 말고, 실제 확인·코드 검토·미확인을 구분해 보고해.
결함은 재현 조건·기대 결과·실제 결과·영향을 남겨 줘. 구현 이해 설명은 A가 맡으니 검증 보고에 집중해 줘.
```

### D 사용자 관점 담당

```text
guide/COMMON.md와 guide/D-USER.md를 읽어 줘. 너는 D 사용자 관점 검토 담당이야.
확인된 사용자·사용 목적과 현재 화면 흐름을 기준으로, 목적 달성을 막는 지점과 예외를 검토해 줘.
확인된 문제, 가정, 추가 질문을 구분하고 영향이 큰 항목부터 보고해.
새 기능을 요구사항으로 확정하거나 코드를 수정하지 마.
```

## 진행과 전달

기본 흐름은 아래와 같습니다. 검토 결과에 따라 관련 단계로 돌아갑니다. 네 대화를 항상 동시에 실행할 필요는 없습니다.

```text
작업자와 A의 설계 → 필요할 때 D 검토 → 작업자가 범위 확정 → B 구현·검사·보고
                                                          ↓
                                    같은 코드 상태에서 병행
                                    ├─ C: 독립 검증·근거 보고
                                    └─ A와 작업자: 실제 구현 이해
                                                          ↓
                                    검증 결과 대조 → 작업자 직접 확인
```

B가 이번 단계의 보고를 마치면 대상 작업 번호·버전과 코드 상태를 A와 C에 전달합니다. Git을 사용한다면 커밋 번호와 미커밋 변경 유무도 포함하고, 사용하지 않는다면 변경 파일과 검사 시작 상태를 기록합니다. 작업자는 B에 검증 대상의 수정을 잠시 멈추도록 알립니다. A는 이 상태의 코드를 설명하고 C는 같은 상태를 검증합니다. A의 설명만으로 검증 통과를 선언하지 않습니다.

C가 검증하는 동안 A와의 새 설계 논의는 별도로 남기고, 검증 대상인 요구사항·TASK.md·코드는 유지합니다. 중간 수정이 필요하면 C에 알리고 변경 상태를 기록한 뒤 영향받는 검사를 다시 진행합니다. C의 결과가 나오면 A와 함께 설명과 실제 동작의 차이, 실패·미확인 항목을 확인합니다.

A에게 구현 이해를 요청할 때는 다음과 같이 전달할 수 있습니다.

```text
B가 이번 작업의 구현과 보고를 마쳤고, C는 같은 코드 상태를 검증 중이야.
이번 TASK와 B의 REPORT, 관련 코드를 읽고 핵심 입력이 처리·저장·출력되는 흐름부터 설명해 줘.
설계할 때 의도한 내용과 실제 구현의 차이를 짚고, 선택 이유는 기록된 사실과 추정을 구분해 줘.
한 번에 핵심 흐름 하나씩 설명하고, 내가 요청하면 이해를 확인하는 질문을 하나씩 해 줘.
C가 아직 확인하지 않은 동작은 검증 대기라고 표시하고, 이번 검증 대상 파일은 수정하지 마.
```

프로젝트에서 아래 이름을 사용하거나 기존 문서에 대응시킬 수 있습니다. 지침 저장소 안이 아닌 실제 프로젝트의 지정 위치에 둡니다.

| 작업 문서 | 주 작성자 | 담을 내용 |
| --- | --- | --- |
| requirements.md | A | 목적, 근거 있는 요구사항, 미확정 사항, 선택·대안·이유·한계와 제외 범위 |
| TASK.md | A | 이번 작업 번호·버전, 범위, 변경 허용 파일, 완료·검증 기준 |
| REPORT.md | B | 대상 작업 번호·버전, 변경, 요구사항과 구현·검사의 연결, 실제 검사 수, 미확인, 한계 |

[TEMPLATES.md](TEMPLATES.md)는 필요한 절만 읽어 기존 문서에 적용합니다. 모든 양식이나 별도 파일을 항상 만들 필요는 없습니다. 중단·새 대화로의 전달이 필요하면 작성 담당을 정해 프로젝트의 HANDOFF.md 또는 기존 보고서에 현재 상태와 다음 한 작업을 남깁니다. 새 대화는 기록을 실제 파일과 대조합니다.

실제 마감에 맞춰 검증·실행 문서·제출 시간을 남기고, 기능 추가를 멈출 시점을 사용자와 정합니다. 상태를 물으면 현재 단계·확인 가능한 남은 시간·필수 미검증 항목·다음 한 작업을 짧게 보고합니다.

C와 D는 우선 대화로 검토 결과를 보고합니다. 별도 파일 기록이 필요하면 먼저 작성 위치와 담당을 정합니다. B가 작업하는 동안 현재 TASK.md는 유지하고 다음 작업은 별도로 논의합니다. 요구사항 변경이 현재 작업에 영향을 주면 B에 알리고 진행 상태를 확인한 후 새 버전을 확정합니다.

기존 대화의 요약만으로 확정하기 어려운 조건은 관련 원문을 확인합니다. 모든 역할에 전체 대화와 모든 파일을 반복해서 전달할 필요는 없습니다.

## 공개 자료의 범위

이 저장소에는 재사용 가능한 일반 지침만 둡니다. 실제 업무·평가 자료, 개인정보, 자격증명, 비공개 코드, 실제 작업 결과와 대화 기록은 넣지 않습니다. 별도 허가 없이 프로젝트 결과물을 이 저장소로 전송하거나 Git push하지 않습니다.

이 가이드는 특정 조직이나 평가의 공식 자료가 아니며, 외부 자료 반입 허용의 근거가 되지 않습니다.

## 참고와 반영 범위

아래 자료의 관점을 참고해 기존 역할 구조에 맞는 지침과 양식을 새로 작성했습니다.

- [ai-workflow-playbook](https://github.com/kwonhj0/ai-workflow-playbook): 질문의 근거와 영향 구분, 방법 비교, 실행 근거 연결, 구현 이해와 인수인계.
- [sk-hynix-2nd-harness](https://github.com/hamjoon2003/sk-hynix-2nd-harness): 중요한 결정과 한계 기록, 미실행 검사를 통과로 보지 않는 원칙, 마감 전 검증 시간 확보.

외부 저장소의 코드·설치기·자동 점검 프로그램은 포함하지 않습니다. 원문의 일정·모델·반입 조건·채점 관련 주장을 현재 작업의 규정으로 적용하지 않습니다.
